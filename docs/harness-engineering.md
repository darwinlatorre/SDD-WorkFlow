# Harness Engineering

A harness is the surrounding discipline that makes work inspectable: durable
context, roles, gates, bounded procedures and evidence. The model is not the entire
system. This framework favors small explicit contracts over an autonomous engine.

Read sources on demand. Recover project/state/spec/progress references, then produce
one compact next-action handoff. Keep decisions linked to their source and checkpoint
derived from effective completion. Do not store duplicate transcripts per step.

Incremental verification reuses evidence only when relevant file-set membership,
bytes, non-secret identities and full procedure definitions still match. A check's
timestamp is not proof of freshness. Separate automated, observable, integration
and static evidence; semantic review complements structural tests.

Human approval and closure remain separate. A failed correction gets one focused
changed-hypothesis retry, then intervention if still no progress. These patterns
aim to reduce wasted context/check work; no measured token, cost or speed benchmark
is claimed. Optional models/skills cannot expand an approved spec.
